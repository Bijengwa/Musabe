# Musabe 10,000 Concurrent-User Scaling Plan

## Target architecture

- 3–6 Node.js API instances behind a load balancer.
- PostgreSQL primary + 2 read replicas (or a managed PostgreSQL HA service).
- Redis for shared rate-limit counters, login locks and live-session coordination.
- Sticky-free HTTP; sessions remain database-backed or move to signed opaque Redis/PostgreSQL sessions.
- SSE through Redis Pub/Sub or a managed live gateway. PostgreSQL LISTEN/NOTIFY may remain for small deployments.
- CDN/static cache for React assets.
- Separate workers for reminders, SMS, exports and other long-running jobs.
- Nginx/ALB connection limits, TLS and `X-Forwarded-*` trust configured once.

## Initial sizing estimate

| Component | Starting production size | 10k target |
|---|---|---|
| API | 4 × 2 vCPU / 4 GB | 8–12 instances, autoscale by CPU and connections |
| PostgreSQL | 4 vCPU / 16 GB, HA | 8–16 vCPU / 64 GB, read replica(s) |
| Redis | 2 GB HA | 8–16 GB HA |
| SSE/live gateway | included on API | dedicated 2–4 instances or managed gateway |
| Static frontend | CDN | CDN |

## Required code changes

1. Replace memory-only `express-rate-limit` and `addrFails` with a shared Redis store.
2. Replace per-process SSE connection ceiling with Redis Pub/Sub and an externally tracked connection count.
3. Run Node in cluster mode or containers; no in-process cron/reminder singleton remains on every instance.
4. Add PgBouncer/transaction pooling for application connections.
5. Move Excel export/import and report generation to a queue.
6. Add database indexes for frequent school/date/user queries.
7. Add health/liveness/readiness endpoints and structured metrics.
8. Load test: 10,000 WS/SSE devices, 2,000 writes/minute, and 20,000 reads/minute.

## Acceptance gates

- P95 API latency below 500 ms.
- P99 API latency below 1.5 s.
- Error rate below 1%.
- SSE reconnect success above 99.9%.
- PostgreSQL connection usage below 70%.
- Redis memory below 70%.
- 99.95% monthly availability target.

## Deployment note

The current `LIVE_MAX_TOTAL=2000` is a deliberate per-process limit. It is not a global 10,000-user setting. A 10k deployment requires Redis Pub/Sub and a dedicated live connection tier.
